# humanizer-skill-creator

**각자 자기 말투용 퇴고 스킬을 만들고, eval로 검증하고 개선하는 도구.**

AI 초안을 “사람답게” 만드는 범용 humanizer는 이미 많다. 문제는 그게 *누구* 이냐다. 대부분의 범용 humanizer는 짧은 평어 단문을 사람 글로 보고, 그 사람의 입버릇·호흡·구두점 습관을 같이 지운다.

여기서 만드는 건 **한 사람 전용 퇴고 스킬**이다. 그 사람 글에서 AI 티만 걷고, 그 사람이 일부러 쓰는 말은 남긴다. 남기는 목록을 저자가 직접 확정하기 때문에 회귀 테스트가 가능하다.

이 저장소는 도구만 담는다. 완성된 스킬은 각자 자기 폴더에 생긴다 — 남의 말투가 여기 섞이지 않는다.

> 만들어진 스킬이 실제로 어떻게 동작하는지는 [demo/index.html](demo/index.html)에 있다. 원고 3문단에서 냄새 아홉 곳을 찾아 다섯 곳만 고치는 과정을 단계별로 펼쳐 두었다.

## 준비물 두 개

시작 전에 이것만 있으면 된다. 없으면 시퀀스가 알아서 멈추고 물어본다.

1. **본인이 쓴 글 1편** (대략 200자 이상). 붙여 넣거나 그 자리에서 쓴다.
2. **지금 고치고 싶은 AI 초안 1편.** 시험용이다. 없으면 나중에 따로 요청받는다.

에이전트가 저장소를 뒤져 “당신 글 같은 것”을 골라 오지 않는다. 그건 당신 문체가 아니라 당신 문체의 추측이다.

## 5분 시작

**1. 설치.**

```bash
git clone https://github.com/imakerjun/humanizer-skill-creator.git
cd humanizer-skill-creator
./install.sh
```

스킬과 커맨드를 개인 폴더로 심링크한다(`~/.claude`, 있으면 `~/.codex`·`~/.cursor`도). 심링크라서 나중에 `git pull`만 하면 갱신이 따라온다. 되돌리려면 `./install.sh --uninstall` — 당신이 만든 스킬은 건드리지 않는다.

**2. 실행.** Claude Code를 다시 열고,

```
/말투-만들기
```

커맨드 없이 “내 말투 스킬 만들어 줘”라고 해도 스킬이 켜진다.

**3. 질문 네 번에 답한다.** 한 턴에 하나씩만 온다.

| 순서 | 묻는 것 | 당신이 하는 일 |
|---|---|---|
| 0a | 어디에 쓸 글인지 | 번호 하나 (블로그·공지·메일·강의·보고서·책·대본…) |
| 0b | 그 맥락의 본인 글 1편 | 붙여 넣기 |
| 1 | 이 표현 남길까요 | `보존` / `줄임` / `모르겠다` — **최대 3번** |
| 2 | 고치고 싶은 초안 | 붙여 넣기 |

`모르겠다`는 정상 답이다. 지우지도, 확정하지도 않고 보류로 기록한다. 두 번 연속이면 질문을 멈추고 바로 시험으로 넘어간다 — 실제로 고쳐진 걸 보면 판단이 생긴다.

**4. 시험을 보고 판정한다.** 당신 초안이 before/after로 온다. “이건 내 말 아니다” 한마디면 다시 돈다.

**5. 평가셋 4개.** 이게 본선이다. 여기까지 와야 v1이다.

## 커맨드 두 개

| 커맨드 | 언제 |
|---|---|
| `/말투-만들기` | 새로 만들 때. `eval`·`improve`를 인자로 주면 그 모드로 |
| `/말투-평가` | 만든 스킬을 실제로 돌려 채점할 때 |

`말투`까지만 쳐도 둘 다 자동완성에 뜬다.

> 예전에 `/말투`로 설치한 사람은 `git pull && ./install.sh`만 하면 된다. 끊긴 옛 링크는 설치할 때 알아서 지워진다.

## 무엇이 만들어지나

`~/.claude/skills/{당신-스킬-이름}/`에 이런 폴더가 생긴다.

```
{skill-name}/
├── SKILL.md              # 퇴고 절차. 체크리스트 표가 정본
├── STYLE-PROFILE.md      # 관찰된 문체 사실 (형용사 인상 아님)
└── eval/
    ├── AUTHOR-TRAPS.md   # 당신이 남기기로 확정한 표현
    ├── cases/{NN-슬러그}/
    ├── grade.py
    ├── judge-rubric.md
    └── results/
```

이름은 소문자·숫자·하이픈, 저자나 장르가 보이게(`minji-blog-voice`, `team-notice-voice`). `humanizer` 단독은 범용과 충돌한다.

## 왜 평가셋까지 가나

문체 스킬은 만든 날에는 다 잘 되는 것처럼 보인다. 무너지는 건 나중이다.

- 모델이 바뀌면 같은 스킬이 다르게 행동한다.
- 체크리스트를 한 줄 고쳤을 때 다른 게 망가졌는지 알 방법이 없다.
- “이번엔 잘 고쳤네”는 기억이지 증거가 아니다.

그래서 케이스를 파일로 고정한다. 세 종류를 심는다.

| 라벨 | 뜻 | 실패 조건 |
|---|---|---|
| `planted` | 심어 둔 AI 냄새 | 수정본에 그대로 남으면 감점 |
| `traps` | 저자가 남기기로 한 표현 | 사라지면 **즉시 실패** |
| `known_borderline` | 고쳐도 그만, 둬도 그만 | 기록만 |

여기에 **클린대조군**(이미 사람이 다듬은 글)을 하나 넣어 과잉 수정을 잡는다. 오탐은 제안이 아니라 본문 훼손이다.

**eval은 채점기가 아니다.** 모델을 실제로 돌리고 그 결과를 기대 조건에 비추는 일이다. 케이스를 아는 쪽이 결과 파일까지 쓰면 아무것도 측정되지 않는다. 실행 규율은 [eval/RUN.md](eval/RUN.md)에 있다.

## 저장소 구조

```
SKILL.md              # 메타 스킬 본체 — 에이전트가 읽는 절차
README.md             # 이 문서 — 사람이 읽는 안내
install.sh            # 심링크 설치·제거
commands/             # /말투-만들기, /말투-평가
examples.md           # 성공 create의 Input/Output 한 쌍
references/           # 대조 절차, 시드 목록, 안티패턴, 설계 출처
templates/            # 복사해서 채우는 골격 (SKILL·STYLE-PROFILE·eval)
eval/                 # 이 메타 스킬 자체의 압력 테스트
demo/                 # 만들어진 스킬이 원고를 고치는 과정 (index.html)
```

`references/`는 필요할 때만 열린다. 처음부터 다 읽지 않아도 된다.

## 만든 스킬을 팀과 나누고 싶으면

기본은 개인 폴더다. 이 저장소에 남의 말투를 쌓지 않는다.

그래도 공유하고 싶으면 **자기 스킬만 따로 저장소로** 올리는 편이 낫다. 문체 프로필과 함정 목록은 개인 기록이고, 남이 그 체크리스트를 복사하면 흉내 스킬이 된다. 가져갈 것은 시퀀스이지 체크리스트가 아니다.

## 만든 배경

설계 출처와 공개 humanizer에서 가져온 것·버린 것은 [references/community-lessons.md](references/community-lessons.md)에 정리해 두었다.

핵심 규율 한 줄은 obra/superpowers의 Iron Law에서 왔다. **실패하는 테스트를 보기 전에 스킬을 고치지 않는다.**
